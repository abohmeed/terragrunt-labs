# 07.3 Values

Pass values into stack units, and wire one unit's output into another unit in the same stack. No AWS account.

## Goal

From `start/live`, make this succeed:

```bash
terragrunt stack run -- apply
terragrunt stack output
```

Three units are generated from one record unit. `plain` keeps the default `terragrunt.values.hcl`. `network` and `service` replace it. After apply, the service `note` output is the network `name` output, a value like `net-smart-cattle`. That string is not in the service values. It comes from the network state.

## `values` and `terragrunt.values.hcl`

A unit reads `values.environment`, `values.prefix`, and `values.note`. Terragrunt loads those attributes from `terragrunt.values.hcl` in the unit directory.

| Where the file comes from | What you wrote | What generate does |
| --- | --- | --- |
| Default | `units/record/terragrunt.values.hcl` | Copied when the `unit` block sets no `values` |
| Replacement | `values = { ... }` on the `unit` block | Writes a new `terragrunt.values.hcl` and discards the default |

The replacement is not a merge. A `values` block that sets `prefix` and omits `note` produces a file with no `note`, and the unit fails when it reads `values.note`. Set every attribute the unit reads.

`plain` sets no `values`, so its generated file matches the default: `prefix = "def"` and `note = "default note"`.

Values are fixed when the stack is generated. They cannot read another unit's state. To pass the network `name` into service, add an `autoinclude` on the service `unit` block. Generate writes `terragrunt.autoinclude.hcl` next to the service unit and merges it on every run. `unit.network.path` becomes `../network` in that file. `inputs` merge key by key, and the autoinclude wins, so `note` is `dependency.network.outputs.name` even though `values.note` is also set.

Mocks cover `validate` and `plan` until network has been applied. `apply` is not in that list. `stack run apply` applies network first, so service reads the real output.

## Layout

```text
start/
  root.hcl
  modules/record/
  units/record/terragrunt.hcl          # reads values.*
  units/record/terragrunt.values.hcl   # default. Leave it.
  live/terragrunt.stack.hcl            # network, service, and the autoinclude
```

`plain` is already in the stack file. Leave that block without a `values` attribute.

## Steps

1. Install the pinned CLIs if you have not (lecture 02.1). `terraform_binary = "terraform"` in `root.hcl` keeps the engine on Terraform 1.17.
2. Read `units/record/terragrunt.hcl` and `units/record/terragrunt.values.hcl`. Leave them.
3. Replace the TODOs for `network` and `service` in `start/live/terragrunt.stack.hcl`. Keep the `plain` block. The network and service blocks are:

```hcl
unit "network" {
  source = "../units/record"
  path   = "network"

  values = {
    environment = "dev"
    prefix      = "net"
    note        = "network unit"
  }
}

unit "service" {
  source = "../units/record"
  path   = "service"

  values = {
    environment = "dev"
    prefix      = "svc"
    note        = "replaced by the network output"
  }

  autoinclude {
    dependency "network" {
      config_path = unit.network.path

      mock_outputs = {
        name = "mock-network-name"
      }

      mock_outputs_allowed_terraform_commands = ["validate", "plan"]
    }

    inputs = {
      note = dependency.network.outputs.name
    }
  }
}
```

4. From `start/live`:

```bash
terragrunt stack generate
cat .terragrunt-stack/plain/terragrunt.values.hcl
cat .terragrunt-stack/network/terragrunt.values.hcl
cat .terragrunt-stack/service/terragrunt.autoinclude.hcl
terragrunt stack run -- plan
```

The plain file is the default, with no generated header. The network file starts with `Auto-generated by the terragrunt.stack.hcl file by Terragrunt` and sets `prefix = "net"`. The autoinclude sets `config_path = "../network"`.

The cold plan is three plans of `Plan: 3 to add, 0 to change, 0 to destroy.` Service `note` is `mock-network-name`. Plain `note` is `default note`.

5. Apply, then read the stack output. `stack output` is its own command. It is not `stack run output`.

```bash
terragrunt --non-interactive stack run -- apply -input=false
terragrunt stack output
```

`stack run apply` adds `-auto-approve`. Service `note` equals the network `name`. Network `name` looks like `net-smart-cattle`. Service `name` is its own pet, prefixed `svc`. Plain `name` is prefixed `def`.

6. Destroy, then remove the generated stack:

```bash
terragrunt --non-interactive stack run -- destroy -input=false
terragrunt stack clean
```

Destroy runs service before network. `stack clean` deletes `.terragrunt-stack/`. State for this lecture lives in that directory, so destroy before you clean.

7. From `start/`, run:

```bash
./check.sh
```

The last line is `PASS  07.3 values`.

The lock file in `units/record` is copied into each generated unit. It pins `local` 2.9.1, `null` 3.3.2, and `random` 3.9.1. The first plan downloads those providers. You do not need AWS credentials.

## If apply stops early

- `values.note` is missing when a `values` block replaced the default file and left `note` out. Set `environment`, `prefix`, and `note` on `network` and on `service`.
- `config_path = "../network"` written by hand in the stack file works only for this layout. Use `unit.network.path` so generate writes the relative path.
- `detected no outputs` on `stack run plan` means the mock allow list does not include `plan`.
- Service `note` still `mock-network-name` after apply means `apply` was added to `mock_outputs_allowed_terraform_commands`, or network was not applied first. Leave the allow list at `validate` and `plan`, and use `stack run apply`.
- `OpenTofu` from `terragrunt run -- version` means `terraform_binary` did not merge from `root.hcl`.
- `hcl fmt --check` fails when the blocks are not aligned with the snippet. From `start/`, run `terragrunt hcl fmt`, then run the checker again.

Compare your stack file with [`solution/live/terragrunt.stack.hcl`](solution/live/terragrunt.stack.hcl). The record unit and the module match `start/`. What the run prints is written up in [`solution/NOTES.md`](solution/NOTES.md).
