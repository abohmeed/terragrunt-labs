# 03.4 Generate

A `generate` block writes a file into the Terraform working copy before init. This lab generates `versions.tf` and `provider.tf` for a module that ships neither file. No AWS account.

## Goal

From `start/`, make `./check.sh` pass. The plan adds three resources, and the working copy contains generated `versions.tf` and `provider.tf`.

## The module

`start/modules/note` has `main.tf`, `variables.tf`, and `outputs.tf`. It has no `versions.tf` and no `provider.tf`. The unit owns those files so every unit can pin the same Terraform and provider versions without editing the module.

`if_exists` controls a second run when the file is already in the working copy:

| Value | Behavior |
| --- | --- |
| `overwrite` | Replace the file |
| `overwrite_terragrunt` | Replace the file when Terragrunt generated it. Leave a hand-written file in place and exit with an error |
| `skip` | Leave the existing file |
| `error` | Exit with an error |

Use `overwrite_terragrunt`. Terragrunt marks a generated file with a `# Generated by Terragrunt` line, and that signature is how the second run recognizes its own file.

## Steps

1. Install the pinned CLIs if you have not (lecture 02.1). `terraform_binary = "terraform"` keeps the engine on Terraform 1.17 when `tofu` is on `PATH`.
2. In `start/terragrunt.hcl`, add these blocks between the `terraform` block and `inputs`:

```hcl
generate "versions" {
  path      = "versions.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<-EOF
    terraform {
      required_version = ">= 1.17.0, < 1.18.0"

      required_providers {
        local = {
          source  = "hashicorp/local"
          version = "~> 2.5"
        }
        null = {
          source  = "hashicorp/null"
          version = "~> 3.2"
        }
        random = {
          source  = "hashicorp/random"
          version = "~> 3.6"
        }
      }
    }
  EOF
}

generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<-EOF
    provider "local" {}

    provider "null" {}

    provider "random" {}
  EOF
}
```

`path` is relative to the working copy, the staged `modules/note` directory. `<<-EOF` strips the indent so the generated HCL starts in column 0. Terragrunt then formats the generated `.tf` file.

3. From `start/`:

```bash
terragrunt run -- version
terragrunt run plan
find .terragrunt-cache -name versions.tf -o -name provider.tf
```

The version line is Terraform 1.17.x. The plan is `Plan: 3 to add, 0 to change, 0 to destroy.` Both generated files start with `# Generated by Terragrunt`.

4. Plan a second time. `overwrite_terragrunt` replaces the files it wrote on the first run.

`start/.terraform.lock.hcl` pins `local` 2.9.1, `null` 3.3.2, and `random` 3.9.1. Terragrunt copies that lock file into the working copy next to the generated `versions.tf`. The first plan downloads the providers. You do not need AWS credentials.

5. Run:

```bash
./check.sh
```

The last line is `PASS  03.4 generate`. The script plans twice, checks the generated files, applies, and destroys.

## If plan stops early

- A `generate` path of `versions.tf` lands in the working copy, not beside `terragrunt.hcl` in git.
- `overwrite_terragrunt` exits with an error when `modules/note` already contains a hand-written `versions.tf` or `provider.tf`. This module leaves both names out so the unit can generate them.
- The provider constraints in `versions.tf` match the lock file (`~> 2.5`, `~> 3.2`, `~> 3.6`).

Compare your unit with [`solution/terragrunt.hcl`](solution/terragrunt.hcl). The module matches `start/`. What the run prints is written up in [`solution/NOTES.md`](solution/NOTES.md).
